1. 배포 완료 기준 재설계 - 사용자 대기 22초 단축

배경

  • 빌더가 매 빌드 새 Pod로 생성되어 의존성 설치가 반복 → 레지스트리 레이어 캐시 적용
  • 빌드 구간은 26.3s 감소했지만 전체 소요는 7.6s만 감소
  • 구간 계측 결과 cache export가 캐시 이득의 71%(18.7s)를 상쇄

분석

  • cache export 26.6s 중 15.6s가 image push 완료 이후 실행
  • 이미 배포 가능한 이미지가 있는데도 다음 빌드용 캐시 완료까지 현재 배포가 대기하는 구조 확인
  • BuildKit 내부 동작과 upstream 이슈를 확인해 export 자체 최적화보다 대기 경로 분리가 효과적이라고 판단

해결

  • cache export는 다음 빌드의 성공 조건, image push는 현재 배포의 성공 조건으로 책임을 분리
  • 현재 배포의 완료 기준을 Job 종료 → image push 완료로 변경
  • 기존 로그 tailer에서 push 완료 마커를 감지해 즉시 배포 시작
  • 감지 실패·빌드 실패 시 기존 Job 종료 대기로 자동 fallback

결과

push 완료 → 앱 실행사용자 체감 배포
Before126s408s
After101s (-25s)386s (-22s)
  • 추가 컴포넌트·리소스 없이 사용자 대기 22초 단축
블로그 - 레지스트리 캐시 적용기: 번 시간의 71%를 도로 가져간 cache export 떼어내기

2. DNS Timeout 원인 규명 - K8s 네트워크와 클라우드 정책 충돌

배경

  • BuildKit Job이 auth.docker.io DNS timeout으로 실패해 빌드·배포가 진행되지 않는 장애 발생

과정

확인 대상검증판단
인터넷 연결같은 Pod에서 git clone 성공배제
CoreDNS재시작 후에도 동일배제
Service / kube-proxyCoreDNS Pod IP 직접 쿼리도 timeout배제
Calico 경로 설정전 노드 routing table 정상route 설정 정상
Cross-node Pod 통신Pod IP ping ✕ · Node IP ping ○패킷 drop 확인
  • OCI 문서와 패킷 경로 비교로 VNIC anti-spoofing과 Calico native routing의 충돌로 원인 확정
  • ipipMode=Always 적용 후 Pod 통신·DNS·BuildKit 빌드 정상화

해결

  • 인프라 설정 변경(source/destination check 해제)과 Calico IPIP 캡슐화 두 대안 비교
  • 오픈소스화·클라우드 이전 가능성을 고려해 벤더 비종속인 K8s 레이어 해결책 선택
  • 설정을 Ansible로 영구화해 클러스터 재구축 시에도 동일하게 적용

결과

  • DNS timeout 제거 · BuildKit 빌드/배포 정상화 · 재구축 시 설정 자동 적용
블로그 - BuildKit DNS Timeout의 진짜 범인: K8s가 깐 길과 클라우드가 막은 길의 미스매치

3. 배포 적용을 Argo CD로 이전 - patch 배포 장애 제거 · API 서버 권한을 테넌트 ns로 한정

배경

  • 포트 변경(java 8080 → node 3000) 배포에서 Service가 422로 거부되는 운영 배포 장애 발생
  • API 서버(core)가 리소스마다 patch/replace를 골라 클러스터에 직접 적용하는 구조
  • 직접 적용하느라 인터넷에 열린 core가 클러스터 전역 권한 보유 - 이름만 알면 모든 ns의 Secret, 모든 Pod exec, kubelet API(nodes/proxy)

분석

  • merge patch가 포트 번호를 키로 병합해 옛 포트가 남고 새 포트가 추가 → 이름 없는 다중 포트로 거부, 로컬 재현 시 Deployment만 바뀐 채 앱 응답 중단
  • 변경 유형마다 replace 분기를 늘려 왔지만, 바뀐 부분만 보내는 명령형 적용은 "이제 없어야 할 것"을 표현하지 못하는 것이 근본 원인

해결

대안배포 장애core 권한
A. replace 분기 추가 (기존)변경 유형마다 분기 계속 추가전역 쓰기 유지
B. core에서 server-side apply필드 삭제는 해결 · 리소스 삭제·드리프트는 직접 구현인터넷에 열린 core가 계속 적용
C. Argo CD (선택)server-side apply + prune으로 해결적용은 외부 비노출 Argo, core는 값만 전달
  • core가 넘기는 건 이미지·포트 같은 값뿐 - 매니페스트 모양은 고정 차트가, 대상 ns·리소스 종류는 AppProject가 제한
  • Argo로 못 옮기는 Secret·exec·ns 삭제는 테넌트 ns RoleBinding으로만 부여, RBAC로 이름 패턴을 표현 못 하는 ns·RoleBinding 생성은 VAP(CEL)로 이름·모양 검사

결과

시나리오Before (core 직접 적용)After (Argo CD)
포트 변경 (장애 재현)422 · 앱 응답 없음분기 없이 정상 배포
플랫폼 정책 변경재배포해도 미반영앱 재배포 없이 약 1분 내 반영
core 탈취 시 닿는 범위전 ns Secret · Pod exec · kubelet테넌트 ns 안만 · 시스템 ns 거부
  • 배포는 운영과 같은 버전(K8s 1.35 · Argo CD 3.5.3) 로컬 클러스터에서 기존 코드를 그대로 돌려 비교, 권한은 운영에서 core 계정으로 can-i · server dry-run 해 확인
  • 운영 앱 10개를 재생성 없이 이관 - 데이터 손실 없이 앱당 1분 미만 중단, 기존 배포 경로 3.9천 줄 삭제
  • core 전역 권한 35 → 16(Argo 이전) → 6(테넌트 RoleBinding · VAP)

4. 파드 지표로 안 보이는 노드 디스크 압박 - 원인 분석과 숨은 15GB 무중단 회수

배경

  • 앱이 몰린 worker1 디스크 사용률 78% - kubelet 이미지 GC(85%)·DiskPressure 축출 임계에 근접 (장애 전 선제 대응)
  • 그런데 Pod 29개의 디스크 사용량(ephemeral-storage) 합은 0.46GB뿐 - Pod 지표로는 원인이 보이지 않음

분석

  • Pod 지표는 컨테이너 쓰기 영역·로그만 셈 → 노드에서 du 바텀업: containerd 이미지 11GB, OS(/usr·/opt) 6.7GB
  • 이미지 정리로 풀리는지 확인 - 캐시 이미지 31개 중 미사용은 2개(0.1GB), 빌드마다 늘어난 태그도 같은 이미지를 가리킴 → 쓰는 양이 아니라 용량 문제
  • 디스크 46.6GB인데 root는 30GB - lsblk·lvs로 OCI Oracle Linux 이미지 기본 LVM이 root + oled 15GB로 분할된 것 확인, oled엔 PCP(성능 수집기) 아카이브 0.3GB만 상주

해결

대안장점리스크
A. 이미지 정리즉시 적용미사용이 0.1GB라 효과 없음
B. boot volume 확장용량 여유무료 한도 판정 불확실 · 볼륨은 줄일 수 없어 되돌릴 수 없음
C. oled 회수 → root 온라인 확장 (선택)추가 비용 없이 노드당 +15GB · 재부팅 없음PCP·kdump 의존 정리 필요
  • 회수 스크립트를 실패 지점마다 멈추도록 설계 - PCP 정지 후 fuser로 점유가 남으면 아무것도 바꾸지 않고 종료, fstab은 umount 성공 뒤에만 수정하고 결과 재확인
  • oled가 이미 없으면 바로 종료 → 같은 스크립트를 다시 돌려도 안전, lvextend + xfs_growfs로 마운트된 채 확장
  • 숨은 의존 2개 발견 - kdump initramfs가 oled를 덤프 대상으로 구워 둠 → kdumpctl rebuild, kubelet은 용량을 시작 때만 읽음 → kubelet만 재시작(컨테이너 유지)

root 용량사용률 (worker1 / worker2)K8s 인식 용량

1. CloudFront 502 원인 규명 - 구간 신규 연결 지연 67% 개선 (15.7 → 5.1ms)

배경

  • CloudFront를 통한 백엔드 요청에서 502 Bad Gateway 발생
  • ALB 직접 요청은 정상, CloudFront의 S3 요청도 정상 → CloudFront-ALB 구간으로 장애 범위 축소

분석

  • openssl s_client로 TLS 연결 확인 → TCP 연결은 성공했지만 ALB가 반환한 인증서 CN과 요청 호스트가 불일치
  • CloudFront의 Origin SNI와 ALB 인증서 도메인이 달라 SNI mismatch로 원인 확정

해결

대안장점리스크
A. SSL Offloading (선택)핸드셰이크 제거 · 인증서 관리 단순화CloudFront–ALB 구간 TLS 미적용
B. 전 구간 HTTPS전송 구간 암호화 유지TLS 오버헤드 · 인증서 추가 관리
C. Host 헤더 조정즉시 적용 가능리다이렉트·쿠키 사이드이펙트
  • 전 구간 TLS가 필수인 규제 요구가 없는 서비스 특성과 성능·운영 복잡도를 함께 비교해 A 선택
  • 잔여 리스크는 AWS 백서로 관리 네트워크의 물리 계층 전송 보호·VPC 테넌트 격리를 검토해 평가 후 수용
  • 별도로 공격면 축소 - Managed Prefix List + Custom Header 검증으로 본인 CloudFront를 거친 요청만 ALB에서 허용

결과

  • 502 장애 해결 및 서비스 정상화
  • AWS CloudShell에서 동일 ALB 기준 n=100 측정 → 15.7ms → 5.1ms, 구간 신규 연결 지연 67% 개선
  • CloudWatch 5xx 알람으로 이상 징후 탐지, Terraform 주석으로 설정 의도 문서화
블로그 - HTTPS가 항상 정답은 아니었다: CloudFront 502 장애 분석
