> **요약**
레지스트리 캐시를 붙이기 전에, 캐시를 올리는 비용이 아끼는 시간보다 큰 건 아닌지부터 재봤습니다. 이미지 push는 쌌고 진짜 비용은 cache export였고, 캐시가 빌드에서 벌어준 시간의 71%를 도로 가져가는 데다 그중 15.6초는 이미지가 레지스트리에 다 올라간 뒤에 돌고 있었습니다. 배포는 이미 가능한 상태인데 사용자는 다음 빌드용 캐시가 올라가기를 기다리고 있던 거였습니다. export가 무거워서라기보다 응답 경로 안에 있다는 위치가 문제였고, 어디까지 끝나야 충분한지는 BuildKit이 아니라 호출하는 쪽만 알 수 있었습니다. 그래서 배포 성공 판정을 Job 종료에서 push 완료로 앞당겼고, **운영 실측으로 22초(부하 편차를 보정하면 25초)를 줄였습니다. Job도, 리소스도, 새 컴포넌트도 늘리지 않았습니다.**
> 

## 들어가는 글

KoDeploy는 GitHub 링크를 넣으면 자동으로 빌드하고 배포까지 해주는 K8s 기반 멀티테넌시 PaaS입니다. 배포 한 번은 빌드 → 이미지 push → 배포 순서로 흘러가고, 사용자가 체감하는 "빌드 시간"은 이 셋의 합입니다.

![](/images/posts/registry-cache-export/01.png)

미뤄두던 레지스트리 캐시를 붙이기로 했습니다. 실제로 올라가 있는 앱 하나(dailo)의 빌드 로그를 열어 보면 매번 똑같은 gradle 의존성을 처음부터 다시 받는 데 상당한 시간을 쓰고 있었는데요. 빌더가 매번 새 파드로 뜨다 보니 지난 빌드가 받아둔 게 다음 빌드로 이어지지 않는 구조였습니다. 캐시를 레지스트리에 두면 이 반복이 사라집니다.

목적지를 레지스트리로 잡은 건 격리 때문입니다. KoDeploy는 사용자 코드를 빌드하는 멀티테넌시라, A 유저의 캐시 레이어(소스가 들어 있음)에 B 유저가 닿으면 그 자체로 사고입니다. 빌더 로컬 디스크나 NFS류 공유 볼륨은 공유가 기본이고 격리가 추가 공사인데, 레지스트리는 ref를 앱 단위로 나누고 토큰을 그 경로에 스코프하면 격리가 저장 구조에서 따라옵니다.

붙이는 것 자체는 플래그 두 줄이면 끝납니다. 걸리는 건 그다음이었습니다. 레지스트리 캐시는 공짜가 아니라서, 매 빌드가 끝날 때마다 캐시를 레지스트리로 올리는 시간이 새로 붙습니다. 시간을 아끼자고 켠 물건이 올리는 비용 때문에 배보다 배꼽이 되는 건 아닐까? 그래서 켜기 전에 이 "올리는 시간"의 정체부터 재보기로 했습니다.

> **용어 정리 - "빌드 캐시"는 두 층위입니다.** 의존성 캐시(`RUN --mount=type=cache`)는 빌드 도중 받는 패키지를 빌더 로컬에 캐싱합니다. 레이어 캐시(`--import-cache` / `--export-cache`)는 빌드 결과 레이어를 저장해 입력이 안 바뀐 스텝을 통째로 건너뜁니다. 이 글이 다루는 건 후자, 그중에서도 캐시를 레지스트리에 밀어넣는 동작인 cache export입니다.
> 

## push와 cache export의 차이

처음에 저는 병목이 네트워크 전송일 거라고 생각했습니다. 그런데 구조를 뜯어 보니 "레지스트리에 올린다"는 동작 안에 성격이 다른 둘이 섞여 있었습니다. 이미지 push와 cache export입니다.

빌드 중에 만들어진 레이어는 아직 이미지가 아닙니다. 압축도 이름도 없는 스냅샷 상태로 파드에 쌓여 있다가, tar로 말아 압축해야 비로소 digest(SHA-256)라는 이름을 갖습니다.

push는 이 digest 목록을 들고 레지스트리에 "이거 있나요?"를 물어본 뒤, 없는 것만 올립니다. 다만 이 확인은 repo 단위라 다른 repo에 같은 blob이 있어도 소용이 없습니다.

캐시에는 여기에 장부가 하나 더 필요합니다. 캐시 키는 스텝을 돌리기 전에 정해지는데 digest는 돌린 뒤에야 나오기 때문입니다. 그래서 빌드가 끝나면 캐시 키와 digest를 이어주는 장부를 새로 쓰고, 그 장부가 가리키는 레이어들을 함께 올립니다. 이 두 가지를 하는 것이 cache export입니다.

주의할 점은 mode=min에서는 최종 이미지에 실제로 포함되는 레이어 위주로 캐시를 내보낸다는 겁니다. 그런데 멀티스테이지 빌드에서 gradle build처럼 시간이 오래 걸리는 작업은 중간 빌드 스테이지에만 있고 최종 이미지에는 안 들어갈 수 있습니다. 그러면 다음 빌드에서 그 비싼 단계를 재사용하지 못할 수 있어서 mode=max를 사용했습니다. 대신 이름을 붙여 올려야 할 레이어가 그만큼 늘어납니다.

캐시를 어디에 두느냐도 여기 걸립니다. 존재 확인이 repo 스코프라, 캐시를 별도 repo에 두면 이미지 push가 이미 올린 레이어를 cache export가 또 올립니다. KoDeploy는 앱마다 `ghcr.io/{owner}/{app}` repo 하나를 쓰고 캐시를 같은 repo의 (`:buildcache`) 태그에 두는데, 그러면 blob 저장소를 공유하니 겹치는 레이어는 다시 올라가지 않습니다.

같은 "레지스트리에 올린다"인데 무엇이 다른지 맞대 보면 이렇습니다.

|  | 이미지 push | cache export (mode=max) |
| --- | --- | --- |
| 장부 | 확정된 manifest 하나 | 빌드 그래프 전체, 매번 새로 계산 |
| 굳히기(압축·digest) | 최종 이미지 레이어만 | push가 안 굳힌 중간 스테이지까지 |
| 업로드 | 바뀐 레이어만 | 바뀐 레이어만 (같은 repo면) |

마지막 줄은 두 열이 같습니다. **전송은 안 늘어납니다. 늘어나는 건 앞의 둘입니다.**

여기까지 보고, 측정을 시작하기 전에 예측을 정리했습니다.

- push는 바뀐 레이어만 올립니다. dailo에서 재빌드마다 바뀌는 건 소스가 담긴 jar 한 장뿐이라, push는 캐시를 켜든 끄든 거의 일정하고 export보다 작을 거다.
- export는 push에 없는 비용을 집니다. 장부를 매번 새로 계산하고, push가 굳히지 않은 중간 스테이지 레이어를 그 자리에서 압축하고, blob마다 존재 확인을 왕복합니다. 같은 레이어면 압축이 스킵되지 않을까 싶지만 digest는 압축을 해야 나오는 값이라, 레지스트리의 중복 제거가 아껴주는 건 전송 바이트지 압축 CPU가 아닙니다. 그리고 캐시는 체인이라 소스를 고치면 그 아래가 전부 깨지니, 소스 수정 재빌드에서 export가 가장 무겁지 않을까?
- 존재 확인은 방금 import한 장부에 digest가 있기에 적혀 있는 blob이라면 건너뛰지 않을까? (이 예측은 뒤에서 틀린 걸로 판명 납니다.)

## 측정

- **대상**: dailo (실운영 앱, gradle 빌더 + JRE 런타임 2스테이지)
- **BuildKit**: `moby/buildkit:v0.30.0-rootless`
- **노드**: worker1 고정 (2 vCPU).
- **시나리오:**
    - **캐시 OFF**: 캐시 플래그 없음. clean 빌드. 기준선.
    - **캐시 ON, 수정 없음**: 전부 히트. 캐시가 낼 수 있는 상한선.
    - **캐시 ON, 소스 1줄 수정**:  실제 재배포는 대부분 이 경우

```docker
# 1단계: 빌드 단계
FROM gradle:8.11.1-jdk17 AS builder
WORKDIR /app
COPY build.gradle settings.gradle gradlew ./
COPY gradle ./gradle
RUN sed -i 's/\r$//' gradlew && chmod +x gradlew
RUN ./gradlew dependencies --no-daemon
COPY src ./src
RUN ./gradlew clean build -x test --no-daemon

# 2단계: 실행 단계
FROM eclipse-temurin:17-jre-jammy
WORKDIR /app
COPY --from=builder /app/build/libs/*.jar app.jar
EXPOSE 8080
ENV SPRING_PROFILES_ACTIVE=prod
ENTRYPOINT ["java", "-jar", "app.jar"]
```

구간은 BuildKit progress 로그를 타임스탬프와 함께 받아(`kubectl logs --timestamps`) 빌드 / push / cache export 셋으로 잘라 측정

```
빌드 구간         : 첫 스텝 시작 ~ "exporting to image" 직전
push 구간         : "exporting to image" ~ "pushing manifest ... done"
cache export 구간 : "preparing build cache for export" ~ 종료
```

cache export 안쪽은 BuildKit이 하위 구간을 직접 찍어줘서 그대로 썼습니다. 참고로 빌드 구간엔 베이스 이미지 pull이 포함돼 있습니다. 빌더가 매번 새로 떠서 매번 받지만, 모든 시나리오에 공통이라 비교엔 문제가 없었습니다.

| 단계 | 캐시 OFF | 캐시 ON, 수정 없음 | 캐시 ON, 소스 1줄 수정 |
| --- | --- | --- | --- |
| 빌드 | 167.4s (164.5~169.4) | 5.0s (4.7~5.6) | 141.1s (137.7~144.4) |
| 이미지 push | 12.7s (11.9~13.9) | 1.4s (1.3~1.6) | 15.8s (14.9~16.3) |
| cache export | — | 2.5s (2.5~2.5) | 26.6s (25.5~27.6) |
| 총시간 | 180.1s (178.4~181.4) | 7.9s | 172.5s (169.1~174.7) |

예측대로 push(15.8초)보다 export(26.6초)가 컸습니다. 다만 "몇 배"쯤 될 줄 알았는데 1.7배였으니 방향은 맞았으나 크기는 틀렸습니다. export 26.6초를 하위 구간으로 나누면 이렇습니다.

|  | 수정 없음 | 소스 1줄 수정 | clean 빌드 (참고) |
| --- | --- | --- | --- |
| 장부 계산 | 0.8s | 10.9s | 14.8s |
| 굳히기 + 왕복 | 1.7s | 16.2s | 22.6s |
| 합계 | 2.5s | 26.6s | 36.8s |

*하위 두 구간의 합(27.1)이 합계(26.6)보다 0.5초쯤 큰 건, 합계는 로그 타임스탬프로 자른 벽시계 시간이고 하위 구간은 BuildKit이 스스로 찍은 값이라 두 작업이 조금 겹쳐 돌기 때문입니다. 판정엔 영향 없습니다.*

백문이 불여일견, 한 런을 blob 단위까지 뜯어보면 이렇습니다. (이 런은 장부 계산 10.0초, 굳히기·왕복 16.0초였습니다.)

```
cache export (#22)                  25.9s
│
├ preparing build cache for export  10.0s   장부를 계산한다
│
├ sending cache export              16.0s
│  ├ writing layer × 22개           각 0.2~0.4s   산술합 5.6초 → 실측 1.4초
│  │                                (병렬로 돌아 짧음. 장부에 digest가 있어 압축 안 함,
│  │                                 존재 확인 HEAD 한 번, 올린 바이트 0)
│  ├ writing layer b917057f         2.0s    새로 굳힌 레이어
│  ├ writing layer 54d130b1         13.3s   새로 굳힌 레이어
│  └ writing config                 1.5s    계산한 장부를 blob으로 올린다
│
└ writing cache image manifest      0.7s    장부가 가리키는 목록을 태그에 건다
```

굳히기가 대부분 레이어 하나(13.3초)에 몰려 있습니다. push가 굳혀놓지 않은, 최종 이미지에 안 들어가는 빌드 스테이지 레이어 — 예측했던 바로 그 자리에 비용이 청구된 겁니다.

틀린 예측도 있었습니다. 트리에 보이듯 22개 blob이 새 데이터를 한 바이트도 안 올리면서 존재 확인만 하러 왕복하고 있었습니다.. 방금 import한 장부에 digest가 그대로 적혀 있는 blob도 예외 없이 물어보러 갔습니다. 왜 그런지는 잠시 뒤에 나옵니다.

효과를 계산해 보면, 빌드+push만 놓고는 180.1초 → 156.9초로 23.2초가 줄었는데 export 26.6초가 새로 붙으면서 총시간은 172.5초, 7.6초(4.2%) 단축에 그쳤습니다. 의존성 다운로드를 통째로 건너뛰고도요.

다만 export 26.6초 전부가 총시간에 얹히는 건 아닙니다. push와 11초쯤 겹쳐 돌기 때문입니다. 실제로 얹히는 몫은 push가 끝난 뒤 export 혼자 도는 15.6초에, CPU를 나눠 쓰며 push를 늦춘 3.1초를 더한 18.7초입니다. export가 아예 없었다면 push가 캐시 OFF 때처럼 돌아 총시간은 빌드 141.1 + push 12.7 = 153.8초였을 겁니다. 이 기준선으로 계산하면 캐시가 빌드에서 벌어준 게 180.1 − 153.8 = 26.3초, export가 도로 가져간 게 172.5 − 153.8 = 18.7초. 번 시간의 71%입니다("export가 없었다면"이라는 반사실 추정치고 n=5라 관찰로만 적어둡니다).

측정 전에 적어둔 예측을 채점하면 이렇습니다.

| 예측 | 결과 | 판정 |
| --- | --- | --- |
| push는 캐시 유무와 무관하게 거의 일정 | 12.7s → 15.8s (+3.1s) | △ 방향은 맞지만 좀 늘었다 |
| push < cache export | 15.8s < 26.6s | O |
| export는 push의 "몇 배" | 1.7배 | X 생각보다 작았다 |
| 수정한 재빌드 export > 수정 없는 재빌드 | 26.6s vs 2.5s (11배) | O |
| 빌드 이득의 상당분을 export가 상쇄 | 26.3초 벌고 18.7초 지불 (71%) | O |

반성할 지점도 하나 있었습니다. 애초에 왜 26초밖에 못 벌었을까?라는 생각이 들었는데 캐시 OFF와 ON의 스텝을 맞대 보니 답이 바로 보였습니다.

| 스텝 | 캐시 OFF | 캐시 ON (소스 1줄 수정) |
| --- | --- | --- |
| 베이스 pull + `gradlew dependencies` | 29.5 + 45.0 = 74.5s | 42.4s (실행 0초, pull만) |
| `gradlew clean build` | 86.9s | 86.8s |

제일 비싼 clean build는 소스를 고치면 무조건 깨져서 구조적으로 캐시가 안 됐습니다(86.9초 → 86.8초). 캐시가 손댈 수 있었던 건 dependencies(45초 → 0초) 하나였고, 26.3초가 사실상 상한이었습니다. export가 얼마나 비싼지는 그렇게 따졌으면서 캐시가 아낄 수 있는 총량은 재볼 생각조차 안 했었습니다. Dockerfile을 캐시 관점으로 한 번만 다시 읽고 생각해도 알 수 있었을 텐데요.

## 문제는 크기만이 아니였습니다

위 계산에 쓴 숫자 하나를 따로 꺼내 봤습니다. push가 끝난 뒤 export가 혼자 도는 시간은 평균 15.6초. export의 절반 이상이 이미지가 이미 레지스트리에 올라간 뒤에 돈다는 뜻입니다.

무겁기도 하고, 응답 경로 안에 있기도 합니다. 둘 다 있어야 문제가 됩니다. 그러니 질문이 둘로 갈립니다. 이걸 더 가볍거나 빠르게 만들 수 있나, 아니면 응답 경로 밖으로 뺄 수 있나.

![](/images/posts/registry-cache-export/02.png)

## BuildKit에 이런 옵션은 없을까

제일 단순한 해법은 목적지를 바꾸는 것입니다. 로컬 디스크에 캐시하면 레지스트리로 내보낼 게 없으니 이 비용은 통째로 사라지죠. 하지만 그 길은 격리를 포기하는 대가라 처음부터 닫혀 있었습니다. 그러면 export는 그대로 두고 더 가볍게 만들 수 있는지를 봐야 하는데, 뭘 만들기 전에 "export를 백그라운드로" 같은 옵션이 있는지 찾아봤습니다. 없었습니다.

대신 upstream(moby/buildkit)에 비슷한 고통이 꽤 있었습니다. 
[**#3299**](https://github.com/moby/buildkit/issues/3299)는 mode=max에서 장부 계산이 몇 분씩 걸려 캐시 이점을 상쇄한다는 보고(2022년부터 open), [**#6008**](https://github.com/moby/buildkit/issues/6008)은 그 직렬화(`CacheChains.Marshal`)가 CPU만 태운다는 보고, 
[**#6123**](https://github.com/moby/buildkit/issues/6123)은 blob이 이미 원격에 있어도 레이어당 왕복이 든다는 보고입니다. 제가 나눈 세 비용과 하나씩 대응됐습니다.

[**#6123**](https://github.com/moby/buildkit/issues/6123) 스레드에서 제 틀린 예측의 답도 있었습니다. "이미 있는 걸로 아는 blob은 안 물어보면 되지 않나"는 제안이 있었지만, 백엔드가 blob을 지울 수 있어서 거절됐습니다. 장부에 digest가 적혀 있다는 것과 그 blob이 아직 거기 있다는 건 다른 얘기였던 거죠. 대신 받아들여진 건 왕복을 없애는 게 아니라 병렬로 돌리는 쪽이었고, 이건 v0.27.0에 들어가 제 측정 버전에도 포함돼 있었습니다(22번 왕복이 1.4초만에 끝난 이유).

하지만 장부 계산도 굳히기도 병렬화는 건드리지 못 했고, push 후 15.6초는 최신 버전에서도 그대로였습니다. upstream의 개선은 전부 export를 더 빠르게 만드는 방향이지, 응답 경로 밖으로 옮기자는 얘기는 어디에도 없었습니다.

생각해 보면 있을 수가 없습니다. BuildKit에게 "끝났다"는 시킨 일이 다 끝났다는 뜻이고, export를 시켜놓고 먼저 반환하면 거짓말이 되기 때문입니다. 어디까지 끝나면 충분한지는 호출하는 쪽, 즉 저 KoDeploy만 알 수 있었던 겁니다. 이미지가 올라가면 배포할 수 있고, export가 실패해도 다음 빌드가 느려질 뿐 이번 배포는 멀쩡하다는 걸요.

## 해법: 기다리는 대상만 바꿨습니다

export가 만드는 캐시는 다음 빌드용이니 이번 사용자가 기다릴 이유가 없습니다. 게다가 이 비용은 드물게 오지도 않습니다. 수정 없는 재빌드의 export는 2.5초지만 소스를 한 줄만 고쳐도 26.6초, 11배가 됩니다. 재빌드는 거의 항상 소스를 고쳐서 하니 export가 가장 무거운 경우가 곧 가장 흔한 경우고, 동기 export의 비용은 평균이 아니라 매번 상한 근처에서 청구됩니다.

설계 두 개를 먼저 접었습니다. export 전용 Job을 따로 두는 방법은 새 파드에 빌더의 로컬 스냅샷이 없어서 풀 리빌드를 다시 돌려야 하니 worker CPU가 2배로 듭니다. ArgoCD처럼 레지스트리를 감시하는 방법은 ghcr.io가 push 웹훅을 안 쏴서 폴링해야 하는 데다, KoDeploy는 이미 그 Job의 로그를 실시간으로 읽고 있는 기능이 있어서 굳이 레지스트리에 "다 됐나요?"를 물으러 갈 이유가 없었습니다.

그래서 Job은 한 줄도 안 건드리고, Core가 "성공"을 판정하는 시점만 앞당겼습니다. Core에는 이미 두 루프가 돕니다. 사용자에게 빌드 로그를 보여주려고 1초마다 파드 로그를 읽는 tailer와, Job이 끝나길 기다렸다 배포하는 `_run_build`입니다. tailer가 push 완료 마커를 발견하면 신호를 올리게 하고, `_run_build`는 그 신호와 Job 종료 중 먼저 오는 쪽을 기다리게 바꿨습니다.

```diff
- success, job_ended_at = await job_task     # (기존) Job 종료까지 — export 포함
+ await _wait_first(push_done, job_task)     # push 완료든 Job 종료든 먼저 오는 쪽
+ if push_done.is_set():
+     success = True                          # 이미지는 이미 올라갔다. 배포로 직행.
```

`_wait_first`인 게 중요합니다. `push_done`만 기다리면 push 전에 빌드가 깨졌을 때(컴파일 에러 등) 마커가 영영 안 떠서 매달리는데, Job 종료를 함께 기다리면 그 경우 Job이 먼저 끝나 기존과 같이 종료합니다. 마커 감지에 실패해도 최악이 "예전처럼 기다리는 것"이라, 이 기능은 실패해도 원래보다 나빠지지 않습니다.

신호를 올리는 tailer 쪽은 이렇습니다.

```diff
  logs = _combined_job_logs(build_id, build_mode)

+ if push_done is not None and not push_done.is_set():
+     exp = _EXPORT_IMAGE_RE.search(logs)                # "exporting to image" 앵커
+     if exp and _PUSH_DONE_RE.search(logs, exp.end()):  # 그 뒤 첫 push 완료
+         push_marker["at"] = now()                      # 계측점 — 노출 시간을 여기서 잰다
+         push_done.set()                                # 트리거 — _run_build을 깨운다

  if logs != last:                                       # (기존) 로그를 DB에 저장
      row.logs = logs
```

tailer는 배포를 안 합니다. push 완료를 발견하면 신호만 올리고 그 시점을 찍고, 배포는 `_run_build`가 원래 자리에서 원래 코드로 합니다. 측정하려고 로그를 뜯어본 게 그대로 해결의 재료가 된 셈인데, 같은 감지 하나가 배포를 앞당기는 트리거이자 운영 실측에서 쓸 노출 시간의 계측점이 됩니다.

> 주의: 캐시를 켜면 `pushing manifest ... done`이 이미지와 캐시, 두 번 찍힙니다. 첫 매치를 잡으면 캐시 push를 오탐하니 `exporting to image` 앵커 뒤의 것만 잡아야 합니다. 로그 마커는 API가 아니라서 빌더 이미지 버전을 고정하고, 같은 마커를 여러 번 읽어도 신호는 한 번만 올리고, 끝내 못 잡으면 기존 대기로 폴백하게 해뒀습니다.
> 

export가 실패하면 `build.status`는 건드리지 않고 경고 지표(`cache_export_failed`)로만 남깁니다. 이번 배포와는 무관하기 때문입니다. 배포가 먼저 끝난 뒤 같은 앱의 새 배포가 들어와 exporter가 둘이 되는 경쟁은, 새 배포 시 이전 Job을 중단하고 파드 종료까지 확인한 뒤 시작하는 기존 규칙이 막아줍니다.

실제 PR에는 세 겹이 더 붙었습니다. early로 빠졌을 때 뒤에서 도는 Job을 회수하는 reap, Job이 실패해도 배포 상태를 덮지 않는 분기(export 실패 ≠ 배포 실패), 예외나 취소로 task가 살아남았을 때 정리하는 finally입니다. 판정을 앞당기는 건 몇 줄인데, 앞당긴 뒤 남는 것들을 감당하는 코드가 꽤나 붙었습니다. (전체 변경은 커밋에 있습니다.)

## 결과 - 운영 실측

여기까지의 벤치는 노드를 고정한 통제 환경이라 "왜 그런가"를 분해하는 용도였고, 체감이 얼마나 좋아졌는지는 실제 배포 경로에서 따로 쟀습니다. 같은 노드에서 소스를 한 줄씩 고쳐가며 캐시 OFF 5회, 동기와 early-trigger를 번갈아 3쌍입니다.

| 구성 | 사용자 체감 | 빌드+push | export 노출분 | push 완료 → 앱 뜸 |
| --- | --- | --- | --- | --- |
| 캐시 OFF | 464s | 365s | — | 99s |
| 캐시 + 동기 export | 408s | 283s | 24s | 126s |
| 캐시 + early-trigger | 386s | 285s | 25s | 101s |

몫이 둘로 갈립니다. 캐시가 번 것(빌드 365 → 283초)은 옵션 하나로 누구나 하는 일이라 이 글의 성과가 아닙니다. early-trigger가 한 일은 그 뒤에 있습니다. 캐시를 켜면 export 때문에 push 후 구간이 99 → 126초로 늘어나 이득 일부를 도로 무는데, 이걸 캐시 없던 시절 수준인 101초로 되돌렸습니다. 

총 체감으로는 22초 단축입니다. push 후 구간에서 아낀 25초(126 → 101)보다 작은 건 이번 early 런들의 빌드가 2초 무거웠기 때문인데, early-trigger는 Job을 안 건드리니 이건 측정 시점의 부하 편차입니다.

export 노출분은 25초로 동기(24초)와 거의 같습니다. 다만 early일 때 export는 rollout과 CPU를 나눠 쓰니, 이 1초는 편차가 아니라 옮긴 자리에서 새로 드는 비용으로 추측됩니다.

## 대가와 한계

공짜는 아닙니다. export가 끝나기 전에 같은 앱의 다음 빌드가 시작되면 그 빌드는 갱신 안 된 캐시를 만납니다. 가상의 걱정이 아니라, 실제로 하루 9번을 몇 분 간격으로 연속 빌드한 유저도 있었습니다. 그래도 감수한 근거는 miss의 대가가 그 한 번의 빌드가 느려지는 것뿐이고 최악이어도 캐시 없던 시절과 같다는 점입니다. 동기 export는 매 빌드마다 전원이 그 비용을 냈으니까요. 실제 miss 비율은 운영 지표(`cache_cold`)가
쌓이는 대로 다시 볼 예정입니다.

근본 해결도 아닙니다. export 비용 자체는 그대로고 사용자에게 보이는 몫만 치웠습니다. 크기를 깎는 개선은 upstream의 몫이고, 제가 정한 건 그 비용을 언제 누가 내느냐였습니다.

## 마치며

push 후 구간에서 25초. 6분 배포의 일부라, 솔직히 처음 숫자를 보고 김이 좀 샜습니다. 그래도 이 25초는 같은 패턴의 재배포마다 매번 빠지는 것이고, 빌드가 캐시로 짧아질수록 비중이 커지는 자리이고, 얻는 데 든 비용이 이미 돌던 루프에 얹은 조건문 하나, Job도 리소스도 새 컴포넌트도 없이 였습니다.

배운 건 둘입니다. 도구가 정의한 "완료"와 사용자에게 필요한 "완료"가 다를 때 그 경계는 도구를 호출하는 쪽에서만 그을 수 있다는 것. 그리고 메커니즘 추론에는 구멍이 있고 그 구멍은 측정을 통해 명확히 보인다는 것 예측 하나는 빗나갔고, 캐시가 아낄 수 있는 총량은 재볼 생각조차 못 했기 때문입니다
