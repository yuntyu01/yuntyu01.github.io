## 0. 가정한 문제

게임 클라이언트가 보내는 로그(유저 행동, 재화 소비, 시스템 에러)를 받아 쌓는 서버를 만든다고 가정했다.

- 로그는 초당 수만 건이 **끊임없이** 들어온다.
- 받은 로그는 유실 없이 쌓여야 하고, 유저별로 찾아볼 수 있어야 한다.
- 컨테이너를 재시작해도 쌓인 로그는 남아 있어야 한다.
- 다른 사람 노트북에서도 `docker compose` 명령 한 줄로 떠야 한다.

받는 방법의 후보는 셋이다. 파일에 바로 쓰기, 큐에 넣기, DB에 넣기.

![파이프라인 구조도](/images/posts/ingame-log-pipeline/01.png)

결론부터 정리하면 이렇다.

- **구조** - 큐로 **수집**하고 파일로 **적재**한다. 세 후보는 배타적 선택지가 아니라 층이 다르며, 각 층에 맞는 것을 결합했다. (→ 1-2)
- **계약** - **"200을 반환한 로그는 반드시 적재된다."** 모든 검증이 이 명제를 겨냥하며, 크래시 주입 2종(consumer/api SIGKILL) 포함 전 시나리오에서 **미적재 0**을 실측했다. (→ 3)
- **실행** - `docker compose up -d --build --wait` 한 줄. 첫 기동(빌드 포함) 19.3초, 부하 중 총 메모리 407MB. (→ 2)

## 1. 선택 - 왜 이 구조인가

### 1-1. 문제 정의와 계약

초당 수만 건이 **계속** 들어온다는 전제에서 핵심 질문은 "소비가 유입을 따라잡는가"다. 소비가 조금이라도 느리면 미처리분이 매초 누적되어 결국 무너진다.

"유실 없이"는 현재는 검증하기 힘들다. 네트워크에서 끊긴 요청은 서버가 그 존재 자체를 모르기 때문이다. 따라서 책임 범위를 **API가 200을 반환한 시점부터**로 정한다.

- "200을 반환한 로그는 반드시 적재된다." → 200 응답 수와 적재 건수를 세어 비교

단일 노트북에서 수만 TPS는 재현되지 않는다. 검증은 낮은 배율에서 **구조적 속성**(수집·적재 경로 분리, 소비의 유입 추종)을 실측하고, 실제 스케일은 **파티션·컨슈머 증설이라는 확장 축**으로 논증한다.

### 1-2. 층위 정리 - 세 후보는 같은 층이 아니다

|  | 역할 | 층위 |
| --- | --- | --- |
| 큐 | 트래픽을 받아내고 완충 | **수집** |
| 파일 | 받은 데이터를 보관 | **적재** |
| DB | 받은 데이터를 보관 + 질의 | **적재** |

큐는 종착지가 아니다. retention이 지나면 데이터가 사라지므로 어떤 큐 기반 설계든 적재가 필요하다. 논의는 "셋 중 무엇을 고를까"가 아니라 **"각 층에 무엇이 맞는가"**로 진행한다.

### 1-3. 수집 층 - 왜 큐인가

큐 없이 수집하면 API가 곧 적재자가 되고, 적재 속도가 수집 속도의 상한이 된다.

- **DB 직행**: 수신이 DB에 동기 결합되면 **DB 장애가 곧 수신 장애**가 된다. 처리량 축에서도 부적합하다. 커밋당 fsync와 커넥션 풀 경합이 상한을 만들어, 지속 수만 TPS를 요청당 동기 INSERT로 받는 형태와는 맞지 않는다.
- **파일 직행**: 부하 대응으로 API를 수평 확장하는 순간 로그가 인스턴스별 파일로 파편화되어 수집 문제가 재발한다.

그리고 두 방식 모두 대규모로 받으려면 결국 큐가 생긴다. 배치 INSERT는 프로세스 안에 메모리 큐를, fluentd·vector류는 호스트에 에이전트 버퍼를 갖는다. 질문은 "큐를 쓸 것인가"가 아니라 **"어차피 필요한 버퍼를 어디에 둘 것인가"**다. 유저별 순서·재처리·다중 소비는 개별 버퍼가 아니라 **공유 로그의 속성**이므로, 버퍼를 생산자의 장애 도메인 밖 전용 계층(브로커)으로 분리한다.

### 1-4. 브로커 비교 - Kafka 채택

|  | Redis Streams | RabbitMQ | Kafka |
| --- | --- | --- | --- |
| 모델 | 인메모리 로그 | 메시지 브로커 (소비=삭제) | 분산 로그 (소비해도 보존) |
| 내구성 | AOF everysec 시 최대 1초 유실 창 | 영속 큐 | 디스크 로그 + 복제 |
| 순서 | 스트림 단위 직렬 | 경쟁 소비 구조에서 깨짐 | 파티션(key) 단위 보장 |
| 재처리(replay) | RAM 잔존분만 | 기본 모델엔 없음 | retention 내 오프셋 되감기 |
| 다중 소비 | consumer group | fanout 물리 복제 | consumer group (독립 진도) |
| 확장 축 | 단일 스레드 병목 | 큐 적체 시 성능 저하 | **파티션 수 = 설계 변수** |

- **Redis Streams 소거** - 셋 중 Kafka와 가장 닮았지만(append 로그·consumer group 차용) 기질이 반대다: Kafka는 디스크가 본체고 메모리가 가속인데, Redis는 메모리가 본체고 디스크(AOF)가 백업이다. 그래서 ① retention이 RAM 용량에 갇혀 replay가 사실상 공허해지고(초당 수만 건 × 수백 바이트 = 시간당 수십 GB) ② AOF everysec의 1초 유실 창이 남으며(닫으면 지연 급등) ③ 스트림 하나가 단일 스레드라 키 파티셔닝을 애플리케이션이 수동 샤딩으로 재구현해야 한다. 트래픽이 초당 수백~수천 건이고 이미 Redis를 운영 중이라면 적합한 후보지만, 규모 전제가 그 구간을 넘는다.
- **RabbitMQ 소거** - 소비=삭제가 기본 모델의 정의적 속성이다. 파이프라인 버그 수정 후 재처리가 불가능하고, 경쟁 소비 구조에서 순서가 보장되지 않는다. 본래 영역은 작업 분배와 라우팅이지 로그 파이프라인이 아니다.
- **Kafka 채택** - 로그 수집의 요구 네 가지, ① 유저별 순서(partition key) ② 재처리(retention + offset reset) ③ 다중 소비(적재·분석이 각자의 진도로) ④ 순서를 유지한 채 처리량을 늘리는 확장 축(파티션)을 별도 모드나 부가 기능 없이 **기본 모델만으로 동시에 충족**한다.
- 표에 없는 Kafka 호환 재구현들도 모델 논증이 동일하게 성립해 남는 것은 자원·지연의 정량 차이뿐인데, 정량은 환경·버전에 종속되어 논증으로 결판나지 않으므로 기본값을 표준(생태계·운영 지식·관리형 경로)에 뒀다.

### 1-5. 적재 층 - 왜 파일인가

원본 로그는 append-only이며 수정·삭제가 없다(이미 발생한 이벤트는 사후에 바뀌지 않는다). 적재층의 요구는 넷이다.

| 요구 | 근거 |
| --- | --- |
| 내구성 있는 순차 쓰기 | "유실 없이 적재" · 재시작해도 보존 |
| 저비용 무한 누적 | 지속 수만 건이 계속 쌓인다 |
| 스키마 수용 | 시나리오가 유저 행동·재화 소비·시스템 에러를 함께 든다 |
| 후속 분석 접근 | 요구로 적혀 있진 않지만 로그를 쌓는 **전제** |

- **DB(RDB·NoSQL 공통) 소거**: 지불하는 비용은 셋인데 받는 편익이 없다. DB의 차별 능력인 인덱스 조회·부분 갱신이 위 요구 표에 없기 때문이다. 즉 **필요 없는 능력의 비용만 지불하는 선택**이다. (RDB는 게임별로 다른 이벤트 필드에 스키마 경직까지 얹는다.)
    - **쓰기 증폭**: 1건이 저널·테이블·인덱스로 나뉘어 여러 번 쓰인다(문서형의 `_id` 인덱스는 끌 수도 없다). 파일 append는 한 번, 순차로 끝난다.
    - **상시 운영비**: 읽지 않는 시간에도 컴퓨트가 켜져 있고, 무한히 쌓이는 볼륨에 비례해 샤딩·백업 부담이 커진다.
    - **추출 홉**: 분석 도구(Athena·Spark)가 파일을 직접 스캔하므로 결국 파일로 내보내야 한다.
- **파일(JSONL) 채택**: 스키마 유동성을 그대로 수용하고, 용량 대비 비용이 가장 낮으며, 분석 도구가 파일을 직접 읽는다. 도커 볼륨과 결합해 **컨테이너 재시작에도 유실되지 않는다**.

### 1-6. 최종 구조 (큐 수집 + 파일 적재)

- **수집**: 큐가 트래픽을 받아내고, 적재 장애를 API로부터 격리한다.
- **적재**: 파일 + 볼륨이 append-only 데이터를 최소 비용으로 영속화한다.
- **조회**: 적재 경로는 유저를 구분하지 않는다. 유저별 조회는 적재 이후 필터링이며, 프로덕션에서는 Athena류가 맡는다.

### 1-7. 설계 결정

**API**

| 결정 | 근거 |
| --- | --- |
| **ack 후 200** (`send_and_wait` · `acks=all` + idempotence) | 전송 확인 없이 응답이면 API 크래시 순간 "200은 나갔는데 브로커 미도달" 구멍이 생긴다(V-4′ 입증). `linger.ms=5` 배칭이 처리량을 지킨다(p99 33.9ms). `acks=all`은 RF=1에선 무의미하나 RF=3 전환 시 코드 수정 없이 켜진다 |
| `key=user_id` | 파티션 내 유저별 순서 보장. 전역 순서는 요구가 아니다 |
| SIGTERM flush | 우아한 종료 시 producer 버퍼 유실 방지 |

**Kafka**

| 결정 | 근거 |
| --- | --- |
| 파티션 3 | 병렬성 상한 선확보. 운영 개시 후 증설은 key 매핑이 바뀌어 순서 연속성이 끊긴다 |
| 토픽 명시 생성 (kafka-init) | auto-create off가 운영 표준. 파티션 수가 전역 기본값이 아니라 토픽 정의에 귀속된다 |
| JVM 힙 512MB 고정 | "한 줄 복제"는 남의 노트북에서 떠야 성립하기에 상한 설정. 부하 중 실사용 총 407MB |

**Consumer**

| 결정 | 근거 |
| --- | --- |
| **flush → fsync → 커밋** (at-least-once) | 커밋 전에 디스크 도달을 확정한다. flush 전에 커밋하면 "커밋됐는데 파일엔 없음"이 되고, flush만 하고 커밋하면 데이터가 커널 캐시에 남아 전원 차단 시 최대 30초치가 같은 상태가 된다. 대가는 최대 1배치 중복인데, 중복은 후처리로 제거할 수 있지만 유실은 복구할 수 없다. (V-4·V-5 A/B) |
| 소스 좌표 임베딩 `_src:{파티션,오프셋}` | 브로커가 부여한 불변·유일 좌표를 각 줄에 덧붙여, consumer 재처리로 생긴 중복을 식별 가능하게 만든다 |
| JSONL 통짜 적재 (ELT) | flush 경계를 하나로 유지하고 쓰기 경로에서 분류 판단을 제거한다. 분류는 읽기 시점으로 미룬다 |
| 시간 파티셔닝 + part 파일 | `dt=/hour=`로 잘라 파일이 무한히 커지지 않고, 시간 범위 단위로 읽거나 지울 수 있다. 파일을 컨슈머별로 두어 `--scale` 시 동시 append 간섭이 없고, 회전은 배치 경계에서만 하므로 flush→fsync→commit 불변식이 유지된다 |

**환경 (compose)**

| 결정 | 근거 |
| --- | --- |
| **api healthcheck** (소켓 probe) | `--wait`가 "리슨 준비 완료"까지 블로킹하게 만들어 기동 직후 수신 실패를 막는다. 검증 중 원인을 찾아 추가한 항목 (실패 92 → 0) |
| 네트워크 분리 (frontend/backend) | 외부에 여는 지점을 api 하나로 제한해, 인증 없는 브로커와 적재 데이터가 호스트에 노출되지 않는다. |
| `container_name` 미지정 | 이름을 고정하면 복제본이 같은 이름을 요구해 충돌한다. compose가 이름을 붙이도록 두어야 `--scale consumer=N` 증설이 가능하다 |

### 1-8. 비용과 운영 부담

- **로컬 자원**: 다른 사람 노트북에서도 떠야 하므로 자원 점유가 요구사항의 일부다. Kafka 힙을 512MB로 제한, 부하 중 전체 스택 407MB. (V-6)
- **선택의 대가(운영 부담)**: Kafka는 후보 중 운영 부담이 가장 크다(파티션 재배치, 리밸런싱, 그룹 모니터링). 부정할 것이 아니라 완화할 대상이다.
- **완화 - 알람은 consumer lag 하나로**: lag은 생산·소비 속도차의 누적이라 소비 측의 어떤 고장이든(컨슈머 사망, I/O 지연, 재시도 루프, 용량 부족) 결국 이 숫자 하나로 드러난다. 원인 지표(CPU·메모리·I/O)는 수집만 하고 알람은 증상만 건다. 원인에 알람을 걸면 오탐과 미탐 양쪽으로 틀리기 때문이다. 판단은 값이 아니라 기울기로 하고, 우상향이면 `--scale consumer=N`으로 대응한다.

### 1-9. 한계와 프로덕션 전환

- **브로커 SPOF**: 브로커 1대·RF=1. 데이터 디렉토리를 볼륨에 마운트해 재시작 복구는 되나, 프로덕션은 브로커 3대 + RF=3 + `min.insync.replicas=2` + `acks=all`로 1대 장애까지 무중단·무유실을 확보한다. API·consumer는 stateless라 수평 확장으로 대응한다.
- **at-least-once의 중복**: 좌표로 식별되는 것은 consumer 재처리 중복까지다. 클라이언트 재전송 중복은 새 produce라 새 좌표를 받아 잡히지 않으며, 닫으려면 클라이언트가 부여한 이벤트 uuid가 필요하다(서버 범위 밖).
- **로컬 내구성의 끝**: flush·fsync·볼륨이 프로세스 크래시·전원 차단·컨테이너 재생성을 각각 막지만, 디스크가 소실되면 로컬 파일은 돌아오지 않는다. 그 구간은 브로커 retention 내 offset 되감기로 복구하며(현재는 CLI 수동), 프로덕션에서는 적재 대상이 S3로 옮겨져 이 층 자체가 사라진다.
- **보존 정책 부재**: 시간 파티셔닝으로 파일은 나뉘지만 오래된 파티션의 삭제·이관은 미구현이다. 데모 규모(수 MB, 단기 실행)에서 디스크 압박이 없어 스코프에서 제외했다. **프로덕션에서는 S3 수명주기 정책이 이 역할을 맡는다.**

### V-3. 지속 유입 소화

| 지표 | 값 |
| --- | --- |
| 부하 중 lag (10s/30s/종료) | 50 → 0 → 0 - **우상향 없음, 소비가 유입을 따라잡고 있다** |
| 부하 A (send_seq · 60,000건 고정) | 41.0초 소요 ≈ 1,463 rps, 전건 200, 적재 60,000 (미적재 0 · 중복 0) |
| 부하 B (hey · 60초 고정, 단일 키) | 2,596 rps, [ p50 - 18.1ms / p99 - 33.9ms / max - 63.2ms ], 155,821건 전건 200 |
| 부하 종료 후 잔여 lag | 0 - 종료 시점에 이미 소진 (밀린 유입 없음) |
| 파일 로테이션 | `ROTATE_INTERVAL=60` 41초 부하 중 경계 1회 통과, part 파일 2개 분할 확인 |

두 부하는 키 분포가 다르다 - hey는 단일 키(파티션 1개), send_seq는 100키(3파티션 분산). 그런데 **파티션 하나만 쓴 hey가 더 빠르다**(2,596 vs 1,463 rps). 파티션 수는 이 구간의 상한이 아니라는 뜻이다 - 컨슈머가 1개면 파티션이 몇 개든 병렬 이득이 없기 때문이다.

차이의 출처는 부하 생성기 쪽이다. send_seq는 파이썬 스레드라 부하 중 클라이언트 프로세스가 CPU 101%로 한 코어에 갇힌다. 즉 1,463 rps는 파이프라인의 상한이 아니라 **부하 생성 스크립트의 상한**이고, 파이프라인 쪽 상한은 api가 정한다(V-6). 절대값은 세션 간 흔들리므로 비교는 같은 세션 값끼리만 한다.

### V-4. consumer SIGKILL

전송 중 consumer를 SIGKILL → 재기동 → 200 목록과 적재 목록 대조 (`scripts/v4.sh consumer`).

| 항목 | 값 |
| --- | --- |
| 200 응답 | **10,000 / 10,000** (클린 기동 직후 전건 200) |
| **200을 받았으나 미적재** | **0** ✓ |
| 중복 (총 10,050 − 유니크 10,000) | 50 - 커밋 전 배치의 재전달분, `_src` 좌표 동일로 식별 |

**예측과 실측의 왕복** - "커밋 전에 처리된 만큼 중복이 날 것"으로 예측했으나 kill 시점을 바꿔가며 시행한 처음 세 번은 중복 0이 관측됐다. 중복은 `flush()`가 끝나고 `commit()` 전인 짧은 구간에서 죽어야 발생하는데, 배치 주기가 짧아(≤500건, 1초 미만) SIGKILL이 그 창을 자주 비껴간다. at-least-once는 "최소 1회"를 뜻하므로 중복 0도 예측이 빗나간 것이지 구현이 잘못된 게 아니다. 네 번째(t=3.1s)에서 그 구간에 들어가 중복 50건이 나왔다.

**중복의 무늬가 설명과 일치한다** - 50건은 세 파티션에 12·16·22건으로 나뉘고 각 파티션 안에서 오프셋이 연속이다(p0은 1163~1174). 커밋되지 못한 마지막 배치가 통째로 재전달된 것이다. 중복된 줄은 `_src`까지 완전히 같다.

```
{"user_id": "user_43", "seq": 4143, ..., "_src": {"p": 0, "o": 1163}}
{"user_id": "user_43", "seq": 4143, ..., "_src": {"p": 0, "o": 1163}}
```

**좌표로 걸러내도 온전하다** - 적재분 전체를 `_src` 기준으로 중복 제거한다.

```bash
docker compose exec consumer sh -c "find /data/logs -name '*.jsonl' | xargs cat" \
  | python3 -c "import sys,json; print(len({(r['_src']['p'],r['_src']['o']) for r in map(json.loads,sys.stdin)}))"
```

```
10000
```

10,050줄이 10,000건으로 정리되고, 이 값이 200 응답 수와 정확히 일치한다. **중복은 걸러지고 유실은 없다** - "중복은 식별 가능, 유실은 0"이라는 설계 의도를 실측이 그대로 닫는다.

### V-4′. api SIGKILL

같은 절차에서 kill 대상만 바꾼다 (`scripts/v4.sh api`).

| 항목 | 값 |
| --- | --- |
| 200 응답 | 8,353 |
| **200을 받았으나 미적재** | **0** ✓ |
| 적재 유니크 | 8,379 (+26) |

**미적재 0의 근거는 응답 순서다.** `send_and_wait`으로 브로커 ack를 받은 뒤에만 200을 반환하므로, 200이 나갔다는 것은 이미 적재됐다는 뜻이다. 전송 확인 없이 응답하는 구현이었다면 버퍼에만 있는 메시지에 200이 나가 여기서 미적재가 관측된다.

**+26건은 반대 방향의 어긋남이다.** ack는 끝났는데 HTTP 응답 직전에 SIGKILL이 들어와, 적재는 됐지만 클라이언트는 실패로 기록한 건이다. 계약이 단방향임을 보여준다. 200을 받았으면 적재를 보장하지만, 실패는 미적재를 보장하지 않는다. ack와 응답 사이의 창은 닫을 수 없어 오류의 방향만 고를 수 있다.

### V-5. 장애 격리

부하 중(t=8s)에 consumer를 정지시켰다. API는 에러 0으로 30,000건 전건 200을 반환했고, 못 읽은 물량이 lag 11,351까지 쌓였다. 하지만 재기동 후 13초 만에 전량 소진됐다(`scripts/v5.sh`).

그 13초의 대부분은 소진이 아니다. 같은 실험을 초당 계측으로 다시 돌리면(피크 10,743) 재기동 8.1초 시점까지 lag이 피크 그대로 유지되다가 9.7초 시점에 0이 된다. 앞의 8초는 컨테이너 기동과 그룹 재조인이고, **순수 소진은 1.6초 이내 - 초당 6,700건 이상**이다. `v5.sh`가 찍는 13초는 여기에 1초 폴링과 "0을 2회 연속 확인" 가드가 얹힌 상한값이다. V-3에서는 부하 생성 스크립트가 병목이라 컨슈머 능력의 하한(유입 1,463건/s 추종)만 보여줬는데, 밀린 물량을 몰아 처리하는 이 실험이 **더 높은 하한을 드러냈다**.

**적재가 멈춰도 수신은 멈추지 않았다. 동기 결합 구조(API→DB 직행)라면 같은 상황에서 수신 자체가 실패한다. 큐 도입의 핵심 근거를 직접 입증하는 실험이다.**

**Fsync A/B, 보증의 가격**: 같은 실험을 `FSYNC=false`로 재실행하면 전건 200, 피크 12,670, 소진 11초다. 켠 쪽이 13초지만 피크는 오히려 낮았고(11,351), 두 값의 차이는 `v5.sh` 폴링 1회(약 2.6초) 안에 들어간다. **이 정도 해상도로는 fsync의 비용을 분리해 낼 수 없었다.** 배치당 fsync 1회를 ≤500건이 상각한다는 설계 근거는 유지되지만, 그 크기를 해당 실험이 재지는 못했다.

### V-6. 자원 점유

| 컨테이너 | 유휴 | 부하 중 | CPU (부하) |
| --- | --- | --- | --- |
| kafka | 275 MB | 354 MB | 69% |
| api | 34 MB | 36 MB | **110%** |
| consumer | 17 MB | 17 MB | 8% |
| **합계** | **326 MB** | **407 MB** |  |

CPU%는 코어 1개가 100%다. 그래서 절대값이 아니라 **각자의 천장 대비 위치**로 봐야 한다. kafka는 JVM 다중 스레드라 여러 코어로 퍼질 수 있어 69%에 여유가 크지만, api는 uvicorn 단일 워커 - 파이썬 프로세스 하나라 GIL 때문에 천장이 ~100%인데 이미 110%로 거기 붙어 있다. 이것이 이 세션의 ~2,600 rps 상한을 만든다. consumer는 8%로 한가하다.

**즉 병목은 kafka가 아니라 api다.** 그리고 **api는 stateless라 워커·레플리카 증설로 풀리며, 설계를 바꿔야 하는 구조적 한계가 아니다.**

### 검증 중 에러사항 - 기동 직후 수신 실패 92건

계약 검증(V-4)을 돌리다 200 응답이 9,908/10,000으로 나와 추적했다. 원인은 consumer 크래시와 무관한 **기동 직후 수신 준비** 문제였다.

1차 가설 "첫 produce의 토픽 자동 생성 지연"은 kafka-init으로 선 생성한 뒤에도 115건(seq 0~114, 완전 연속)이 실패해 **기각**했다. 
실제 원인은 api healthcheck 부재였다. `--wait`가 컨테이너 running까지만 보장하는데, uvicorn은 lifespan(producer 시작) 완료 후에야 리슨을 열기 때문에 그 사이 창에서 도커 프록시가 접속을 받았다가 reset했다. 
소켓 probe healthcheck를 추가해 `--wait`가 "리슨 준비 완료"까지 블로킹하게 하자 클린 기동 직후 10,000건 **전건 200(92 → 0)**이 됐다.

**readiness는 "프로세스가 떴는가"가 아니라 "요청을 받을 수 있는가"로 판정해야 한다.**
`--wait`의 기본값(running)은 전자여서, 후자를 묻는 healthcheck를 명시해야 한다. 그 결과가 1-7의 api healthcheck 결정이다.

## 4. AWS로 옮긴다면 - 설계와 Terraform

**구성**: ALB(public, 2AZ) → ECS Fargate(private, 2AZ) → Kinesis Data Streams → Firehose → S3

![AWS 아키텍처](/images/posts/ingame-log-pipeline/02.png)

로컬 compose 구조를 관리형 서비스로 치환한 **동형 구조**다.

| 로컬 (compose) | AWS |
| --- | --- |
| Kafka (파티션) | Kinesis Data Streams (샤드) |
| Consumer + 도커 볼륨 JSONL | Firehose → S3 |
| `dt=/hour=/part-*` 레이아웃 | Firehose S3 파티셔닝 - 경로 모양 동일 |
| backend 네트워크 (비노출) | private subnet |
